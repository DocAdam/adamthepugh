TeraCreators Help

Summary​

TeraCreators Help is a documentation project I built to turn scattered, community-sourced game knowledge into something clearer, more structured, and easier to use.

The source material largely came from Discord discussions around TeraCreators games. That meant useful information existed, but it was mixed in with repeated questions, fragmented answers, transitory issues, and casual conversation. The job was not just to collect information. The job was to identify what was worth keeping, shape it into a repeatable help model, and publish it in a way that people could actually navigate.

The problem​

Community chat is full of useful information, but it is a terrible long-term help system.

Even when good answers exist, they are often:

  • buried in long threads
  • repeated over and over
  • phrased inconsistently
  • mixed with noise, bugs, or one-off comments
  • difficult for new users to find and trust

That was the main problem this project set out to solve.

What I wanted to build​

I wanted to build a help site that felt more like actual documentation than a pile of exported chat.

That meant:

  • organizing information by game
  • separating content into useful page types
  • filtering out temporary noise
  • rewriting material into clearer language
  • creating a structure that could scale as more content was added

What I built​

The result is a Docusaurus-based help site for TeraCreators games, published through GitHub Pages and supported by GitHub Actions.

The site includes game-specific sections such as:

  • Havoc Hotel 3
  • Havoc Hotel 2
  • Havoc Hotel 1
  • DnD Zombie Dragon Adventure
  • Raptor Heist

Within those sections, content is grouped into repeatable help categories such as:

  • Overview
  • Tips
  • Tasks
  • FAQ
  • References
  • Terms
  • Rescues where applicable

This creates a documentation pattern that is easier to browse, easier to expand, and much more useful than chat history.

How I approached the work​

This project required more than copying source material into pages.

The real work included:

  • reviewing large amounts of community discussion
  • identifying repeated and stable knowledge
  • separating evergreen help from temporary issues
  • simplifying and reorganizing instructions
  • creating consistent page patterns
  • deciding where screenshots or example images would help
  • shaping content for navigation rather than chronology

In other words, I treated it like a real documentation problem.

Why this is a strong example of my work​

This project pulls together several things I do well:

Turning messy information into usable help​

The core challenge was taking useful but messy source material and making it navigable.

Building structure where none existed​

The site needed categories, naming, page types, and editorial boundaries.

Making judgment calls​

Not everything in a chat log belongs in documentation. A big part of the work was deciding what to keep, what to rewrite, and what to leave out.

Working practically with tools​

This project also reflects hands-on comfort with documentation tooling, static site structure, Markdown-based content, GitHub workflows, and fast iteration.

Tools and workflow​

The public repo uses:

  • Docusaurus
  • GitHub Pages
  • GitHub Actions
  • Markdown
  • a structured docs hierarchy built around repeatable content types

Outcome​

The result is a community-informed help site that is easier to search, browse, share, and maintain than the source material it came from.

It is also a good example of the kind of documentation work I like most: real users, imperfect source material, evolving needs, and a chance to turn chaos into something useful.
