Experiments

I like projects that let me test ideas, structures, workflows, and lightweight solutions without needing a huge formal setup first.

That does not mean random tinkering for its own sake. It means I like experimenting in practical ways that help me learn faster, validate an approach, or make something more usable.

What I mean by experiments​

For me, experiments usually involve things like:

  • trying a different information structure
  • testing a docs workflow
  • building a lightweight help site
  • refining templates
  • exploring content models
  • using simple tooling to reduce repetitive work
  • seeing whether an idea becomes more useful when it is structured differently

Why experiments matter in my work​

A lot of documentation problems are easier to solve when you are willing to prototype.

Sometimes it is faster and more revealing to build a workable version than to keep talking abstractly about what should happen.

That mindset helps with:

  • information architecture
  • content organization
  • workflow decisions
  • static site structure
  • documentation templates
  • practical process improvements

What this says about how I work​

I’m comfortable learning in public through the work.

That includes being willing to:

  • try a structure
  • test an idea
  • revise quickly
  • keep what works
  • throw away what does not

I think that mindset is useful in documentation because a lot of the work improves through iteration, not through pretending the first model is perfect.

The point​

The point of experiments is not novelty.

The point is to learn something useful, make progress, and improve the system or content in a way that can actually hold up.
